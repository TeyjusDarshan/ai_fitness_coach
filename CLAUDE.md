# AI Fitness Coach

## Database Schema (Supabase)

Project: `khwrrvmejvrupokvfwvf` ("AI powered Fitness trainer", region `ap-northeast-1`, Postgres 17.6).

> ⚠️ **RLS is disabled on every table below.** All 10 tables are exposed to the `anon`/`authenticated` roles — anyone with the publishable key can read or write every row. This was originally tolerable while the data was public reference content (exercise library); that condition has now been **triggered**, not just theoretical — `user_profiles`, `sessions`, `session_exercises`, and `session_day_logs` hold real per-user data (generated profiles, workout sessions, prescribed exercises, workout-day progress) and are still exposed with no RLS. This is a known, accepted gap pending an auth layer, not an oversight. Remediation SQL is available on request — don't apply it blind, since enabling RLS with no policies blocks all access.

> The exercise-library schema (`movement_types`, `equipment`, `joints`, `exercises`, `exercise_loaded_joints`, `exercise_relationships`) is sourced from `utilities/workout_builder/data/exercises.csv` and `relationships.csv`, migrated via `utilities/scripts/migrate_exercises_to_supabase.py` (idempotent — safe to re-run after editing the CSVs). Populated as of this writing: 66 exercises, 203 joint links, 110 relationships.

### Entity overview

`exercises` is the hub table. `movement_types`, `equipment`, and `joints` are lookup tables. `exercise_loaded_joints` is a many-to-many join between `exercises` and `joints`. `exercise_relationships` is a self-referential edge table (progression/regression links between exercises). `user_profiles` holds one generated profile per user; `sessions` holds one row per generated workout plan for a user; `session_exercises` is a join table between `sessions` and `exercises` recording the prescribed sets/reps per exercise slot, plus per-set completion progress; `session_day_logs` tracks start/completion timestamps for each individual day within a session's plan.

```
movement_types ─┐
                ├─< exercises >─┬─< exercise_loaded_joints >─ joints
equipment ──────┘               └─< exercise_relationships >─ exercises (self-referential: from/to)
                                 └─< session_exercises >─ sessions >─ user_profiles
                                                             └─< session_day_logs >─ sessions
```

### Lookup tables

| Table | Columns | Notes |
|---|---|---|
| `movement_types` | `id` PK, `name` unique | squat, push, pull, hinge, lunge, carry, rotation |
| `equipment` | `id` PK, `name` unique | bodyweight, resistance bands |
| `joints` | `id` PK, `name` unique | ankle, knee, hip, spine, shoulder, elbow, wrist |

### `exercises` — hub table

Maps to `exercises.csv`. The CSV's `loaded_joints` (semicolon-delimited) is normalized into `exercise_loaded_joints`.

| Column | Type | Notes |
|---|---|---|
| `id` | int4 PK | `GENERATED BY DEFAULT AS IDENTITY` — CSV IDs can be inserted explicitly |
| `name` | varchar | |
| `movement_type_id` | int4, nullable, FK → `movement_types.id` | no cascade |
| `orientation` | varchar, nullable | check ∈ `horizontal, vertical` (NULL where CSV blank) |
| `dominant` | bool, nullable | |
| `equipment_id` | int4, nullable, FK → `equipment.id` | single-valued per exercise; no cascade |
| `min_reps` / `max_reps` | int2, nullable | rep range |
| `avoid_if` | text, nullable | contraindications |
| `on_board` | bool, default `true` | |
| `board_x` / `board_y` | float8, nullable | board coordinates |
| `created_at` | timestamptz, default `now()` | |

### `exercise_loaded_joints` — many-to-many join

Composite PK. Populated from the semicolon-delimited `loaded_joints` column in `exercises.csv`.

| Column | Type | Notes |
|---|---|---|
| `exercise_id` | int4, FK → `exercises.id` | `ON DELETE CASCADE` |
| `joint_id` | int4, FK → `joints.id` | no cascade |

PK: (`exercise_id`, `joint_id`).

### `exercise_relationships` — self-referential edges

Maps to `relationships.csv`. Each row links a `from` exercise to a `to` exercise with a direction.

| Column | Type | Notes |
|---|---|---|
| `id` | int4 PK | `GENERATED BY DEFAULT AS IDENTITY` |
| `from_exercise_id` | int4, FK → `exercises.id` | `ON DELETE CASCADE` |
| `to_exercise_id` | int4, FK → `exercises.id` | `ON DELETE CASCADE` |
| `type` | varchar | check ∈ `progression, regression` |
| `reason` | text, nullable | e.g. "Lack of strength", "RIR > 3 and hit rep ceiling" |

Unique: (`from_exercise_id`, `to_exercise_id`, `type`).

### `user_profiles` — generated client profile per user

Populated by the Flask `/workout-plan` endpoint (`backend/app.py`) via `WorkoutPlanRepository.upsert_user_profile`. **Upsert-by-`user_id`, not versioned** — each new generation for a user overwrites the previous profile; there is no history table.

| Column | Type | Notes |
|---|---|---|
| `user_id` | text PK | caller-supplied id (e.g. `"usr_10235"`), not a Supabase-auth UUID |
| `profile` | jsonb | full generated profile (`demographics`, `goals`, `experience`, `health`, `availability`, etc. — see `agents/mock_data_v1.py` for the shape) |
| `created_at` | timestamptz, default `now()` | |
| `updated_at` | timestamptz, default `now()` | bumped on every upsert |

### `sessions` — one row per generated workout plan

Populated by `WorkoutPlanRepository.create_session` after a successful generation. Plan-level metadata only — the per-exercise prescriptions live in `session_exercises`.

| Column | Type | Notes |
|---|---|---|
| `id` | int4 PK | `GENERATED BY DEFAULT AS IDENTITY` |
| `user_id` | text, FK → `user_profiles.user_id` | no cascade |
| `plan_type` | varchar | `3_day` \| `4_day` |
| `plan_selection_reason` | text, nullable | |
| `medical_clearance_warning` | text, nullable | |
| `coach_notes` | text, nullable | |
| `safety_summary` | jsonb, nullable | `{excluded_movements, excluded_joints, excluded_equipment}` |
| `completed` | bool, default `false` | |
| `created_at` | timestamptz, default `now()` | |
| `completed_at` | timestamptz, nullable | set when marked completed |

Partial unique index `sessions_one_unfinished_per_user` on `(user_id)` where `completed = false` — enforces at most one unfinished session per user, matching the endpoint's short-circuit logic (`POST /workout-plan` returns the existing unfinished session instead of generating a new one) and guarding against duplicate inserts from a racing/retried request.

### `session_exercises` — join table between `sessions` and `exercises`

One row per prescribed exercise slot within a non-rest day of a session. Deliberately does **not** duplicate `name`/`movement_type`/`equipment`/`orientation`/`dominant` (joined in from `exercises` at read time) or `day_label`/`split_name`/`is_rest_day` (reconstructed from the fixed `DAY_TEMPLATES[plan_type]` skeleton in `agents/prompts_v1.py` using `sessions.plan_type` + `day_number`).

| Column | Type | Notes |
|---|---|---|
| `id` | int4 PK | `GENERATED BY DEFAULT AS IDENTITY` |
| `session_id` | int4, FK → `sessions.id` | `ON DELETE CASCADE` |
| `exercise_id` | int4, FK → `exercises.id` | no cascade |
| `day_number` | int2 | 1–7, matches `DAY_TEMPLATES[plan_type].schedule[].day_number` |
| `category` | varchar | check ∈ `primary, secondary` — which slot list this exercise fills |
| `slot_label` | varchar, nullable | e.g. `"Hinge"`, `"Push (Horizontal)"` — echoes the slot label from `DAY_TEMPLATES` |
| `sets` | int2, nullable | |
| `reps` | varchar, nullable | |
| `rep_range` | varchar, nullable | |
| `note` | text, nullable | |
| `created_at` | timestamptz, default `now()` | |
| `completed_sets` | jsonb, default `[]` | boolean array sized to that row's `sets` (e.g. `[false, false, true]`); one entry per prescribed set, toggled independently as the user checks sets off during a workout |

`completed_sets` is written to through the `set_session_exercise_set(p_session_exercise_id, p_set_index, p_completed)` Postgres function (a single atomic `jsonb_set` update), not a client-side read-modify-write — two rapid toggles on different indices of the same row would otherwise race and silently lose one of the updates.

### `session_day_logs` — per-day progress within a session

Tracks start/completion timestamps for each individual day (`day_number`) of a session's plan, separately from `sessions.completed`/`completed_at` which track the whole multi-day plan. Populated by `WorkoutPlanRepository.start_day` / `complete_day` (`backend/repository/workout_plan_repository.py`), driving the PWA dashboard's per-day status (rest / completed / next / upcoming) and the end-of-day summary screen's Total Time stat.

| Column | Type | Notes |
|---|---|---|
| `id` | int4 PK | `GENERATED BY DEFAULT AS IDENTITY` |
| `session_id` | int4, FK → `sessions.id` | `ON DELETE CASCADE` |
| `day_number` | int2 | 1–7, matches `DAY_TEMPLATES[plan_type].schedule[].day_number` |
| `started_at` | timestamptz, nullable | set once, on first `start_day` call for this (session, day) — never overwritten by a later re-entry into the same day |
| `completed_at` | timestamptz, nullable | set when the day's summary screen is reached (`complete_day`) |
| `created_at` | timestamptz, default `now()` | |

Unique: (`session_id`, `day_number`) — enforces one log row per day per session, and makes `start_day`/`complete_day` idempotent upserts. When every non-rest `day_number` in a session's `DAY_TEMPLATES[plan_type]` has a `completed_at`, `complete_day` automatically calls `mark_session_completed` to close out the whole plan.

### Notes on FK delete behavior

`movement_type_id` and `equipment_id` on `exercises`, and `user_id` on `sessions`, and `exercise_id` on `session_exercises`, have no cascade, so deleting a referenced row is blocked while referenced. The join/edge tables (`exercise_loaded_joints`, `exercise_relationships`, `session_exercises` and `session_day_logs` via `session_id`) cascade on delete from their parent (`exercises` / `sessions` respectively). Indexes exist on all FK columns.
