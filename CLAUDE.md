# AI Fitness Coach

## Database Schema (Supabase)

Project: `khwrrvmejvrupokvfwvf` ("AI powered Fitness trainer", region `ap-northeast-1`, Postgres 17.6).

> ⚠️ **RLS is disabled on every table below except `cardio_exercises` and `ingredient_nutrition_reference`.** The other 37 tables are exposed to the `anon`/`authenticated` roles — anyone with the publishable key can read or write every row. This was originally tolerable while the data was public reference content (exercise library); that condition has now been **triggered**, not just theoretical — `user_profiles`, `plans`, `sessions`, `session_exercises`, `session_exercise_set_logs`, `session_exercise_rpe`, `session_cardio_logs`, `user_joint_pain`, `user_period_logs`, `session_analysis`, `workout_comments`, `session_clarifications`, `clarification_replies`, `coach_suggestion_runs`, `exercise_suggestions`, `ai_usage`, `inbound_messages`, `whatsapp_conversations`, `meal_reminders`, and the diet tables `meal_logs`, `meal_log_items` and `meal_log_item_ingredients` hold real per-user data (what she ate, her food recordings and transcripts, generated profiles, weekly plans, scheduled workout days and their progress, prescribed exercises, per-set rep logs, RPE, per-step cardio logs, reported joint pain, logged period days, generated LLM workout summaries, health notes taken from voice feedback, WhatsApp replies and phone numbers, AI Coach suggestions, per-client AI spend, every WhatsApp message with its transcript and route, when each client last messaged, which meal reminders she was sent) and are still exposed with no RLS. This is a known, accepted gap, not an oversight. Remediation SQL is available on request — don't apply it blind, since enabling RLS with no policies blocks all access.
>
> The one exception is `cardio_exercises` (the cardio circuit, library data): RLS is **enabled** with a read-only `cardio_exercises read` policy for `anon`/`authenticated`, so the app can read it but only the dashboard / service-role key can change it. Cardio progression state lives on `sessions` rows and is as exposed as the rest. `ingredient_nutrition_reference` (reference data) is set up the same way, with a read-only `ingredient_nutrition_reference read` policy.
>
> This includes the passkey-auth tables (`user_passkeys`, `auth_challenges`, `auth_sessions`, `passkey_enrollment_tokens`): the API-level passkey sign-in is only as strong as the secrecy of the publishable key, since anyone holding it can insert an `auth_sessions` row (or their own passkey) for any `user_id` and impersonate that user. Kept this way deliberately (decision 2026-09-27) because the backend's `SUPABASE_KEY` is the publishable key. The fix is to switch the backend (and `voice_processor`) to the secret/service-role key, which bypasses RLS, and then enable RLS on these tables.

> The exercise-library schema (`movement_types`, `equipment`, `joints`, `exercises`, `exercise_loaded_joints`, `exercise_relationships`) is edited in the Workout Builder board (`utilities/workout_builder`, `.venv/bin/python utilities/workout_builder/app.py` → http://localhost:8765), which reads and writes these tables in Supabase directly — there is no CSV copy or migration step any more (the old `exercises.csv` / `relationships.csv` / `migrate_exercises_to_supabase.py` flow was removed; git history has them). The board saves its whole state on each change and the server writes only the differences; it refuses to delete an exercise that `session_exercises` still references (no-cascade FK) — take it off the board instead. It offers only `progression`/`regression` links, matching the table's check. Plan progression follows only one progression and one lack-of-strength regression edge per exercise, so avoid drawing more. Populated as of this writing: 66 exercises, 203 joint links, 108 relationships.

### Entity overview

`exercises` is the hub table. `movement_types`, `equipment`, and `joints` are lookup tables. `exercise_loaded_joints` is a many-to-many join between `exercises` and `joints`. `exercise_relationships` is a self-referential edge table (progression/regression links between exercises). `user_profiles` holds one generated profile per user; `user_joint_pain` holds one row per (user, joint) the user has reported pain for. Workouts form a three-level hierarchy: `plans` holds one row per weekly workout plan for a user; `sessions` holds one row per **training day** of a plan (its `day_number`, `scheduled_date`, and start/completion timestamps); `session_exercises` is a join table between `sessions` and `exercises` recording the prescribed sets/reps per exercise slot of that day. `session_exercise_set_logs` and `session_exercise_rpe` track per-set rep completion and per-exercise RPE against a `session_exercises` row; `session_analysis` holds one LLM-generated Tanglish summary per session, written by the standalone `voice_processor` service (see below), which also writes `workout_comments` (structured coach notes from the client's voice notes and replies) and `session_clarifications` / `clarification_replies` (the questions asked after the summary and her WhatsApp answers) — see "Voice-feedback agent" below. Cardio days are `sessions` rows with `kind = 'cardio'` (no `session_exercises`); they run the whole `cardio_exercises` circuit — see "Cardio days" below. The passkey-auth tables — `user_passkeys`, `auth_sessions`, `passkey_enrollment_tokens`, `auth_challenges` — hang off `user_profiles` (see "Passkey authentication tables" below).

```
movement_types ─┐
                ├─< exercises >─┬─< exercise_loaded_joints >─ joints
equipment ──────┘               └─< exercise_relationships >─ exercises (self-referential: from/to)
                                 └─< session_exercises >─ sessions >─ plans >─ user_profiles ─< user_joint_pain >─ joints
                                       ├─< session_exercise_set_logs   │
                                       └─< session_exercise_rpe        └─< session_analysis (one per session)
```

`plans.parent_plan_id` links each auto-progressed plan to the plan it was progressed from.

### `sessions` — one row per training day of a plan

One row per non-rest day of a plan's `DAY_TEMPLATES[plan_type]` schedule (rest days have no row). Created alongside the plan by `create_plan` / `create_progressed_plan`. Drives the PWA dashboard and the end-of-day summary screen's Total Time stat. `GET /api/users/<user_id>/dashboard` returns `workouts` — one panel per session: this plan's last two past ones (completed or missed; earlier weeks aren't looked up), then every scheduled one, each with `status` (completed / missed / scheduled), a display `date` (completion date in `APP_TIMEZONE`, else `scheduled_date`), `is_next`, `can_start` (scheduled for today) and its exercises with set logs and RPE, for the panel's View screen (`/workout/<session_id>`). Each panel also carries `is_today` (completed or scheduled today — the PWA's Today card) and `duration_seconds`. **Start-up:** the PWA makes one call, `GET /api/app/start` (`backend/app.py`), which returns `me` (as `/api/auth/me`) and the `dashboard` (or `dashboard_error` `{status, error}` — 404 when she has no plan), read in parallel (past workouts aren't fetched until the Your Workouts page's Past tab is opened, and again after any dashboard reload), while `frontend/src/preload.ts` loads the 3D plant chunk and the illustrations (capped at 2.5 s); the dashboard opens once all of that is in, and doesn't reload it if it's under 10 s old (`refreshDashboard({skipIfFresh})`). The backend's Vercel function runs in `hnd1` (Tokyo, `vercel.json` `regions`), next to the database — it was in the default `iad1` (US), where every query crossed the Pacific. The LangChain agents and the AI Coach's Anthropic client are imported on first use, not at cold start. The PWA dashboard (`screens/DashboardScreen.tsx`, cards in `components/DashboardCards.tsx`) is: a greeting; the **Today's Workout** card (Start / Continue Workout; "Done for Today" with the time taken; on a rest day the next workout with View), showing the workout's length (cardio: the circuit estimate; strength: `profile.availability.session_duration_minutes`), a "Week N" chip (`week_number` on the dashboard response: how many of her plans were created up to the current one, `week_number` in the plan repo), the strength/cardio illustration (`frontend/public/illustrations/`) and the coach notes as one tappable line; the **Your Garden** card; and the next upcoming workout with **See All** → `/workouts` (`WorkoutsScreen`: Upcoming and Past tabs, the app version at the bottom). Past lists every past workout across all plans, ten at a time, through `GET /api/users/<user_id>/past-workouts?offset=&limit=` (own user only; newest first via `get_user_workout_history`, coach-only fields dropped; `limit` clamped 1–20, default 2; returns `total`/`completed`/`missed` for the section's counts). The dashboard also returns `points` — 25 (`POINTS_PER_WORKOUT`) per completed session across all of the user's plans (`count_completed_sessions`; derived, not stored, so missed sessions earn nothing and period sessions count). The PWA shows points as **XP** and turns them into plant levels (`frontend/src/plant3d/levels.ts`: levels 1–4 cost 25 each, 5–8 50 each, 9–11 100 each, so 600 points / 24 workouts is fully grown at level 11), each with a stage name (`STAGE_NAMES`: Empty Pot, Seedling, First Leaf, Young Plant, Leafy Plant, Budding, First Bloom, New Buds, Blooming, Flowering Bush, Butterfly Visit, Fully Grown). The plant is a 3D potted plant (`PlantScene`, three.js, ported from the `plant/` prototype, one growth step per level; lazily loaded): small on the dashboard's Your Garden card (stage, XP, a bar with "N more workouts to <stage>", View Garden) and full screen on `/garden` (`GardenScreen`: stage | XP pill, falling petals and sparkles, the same progress bar; pieces in `components/Garden.tsx`). After a workout the PWA goes cool-down video → `/day/:n/grow` → `/day/:n/summary`: the grow screen is what calls `POST /api/sessions/<id>/complete` (whose response also carries `points` and `points_earned` — 25 the first time, 0 when re-completing), shows the plant full screen in the Garden page's look earning the XP and growing a stage on a level-up ("You reached <stage>!"), then hands the result to the summary screen (router state) so it isn't completed twice; the summary screen still completes on its own after a reload. With nothing earned it goes straight to the summary. The step last shown is kept in `localStorage` so a new level grows in with sparkles. It also still returns the per-day `days` list (rest / completed / missed / next / upcoming, plus `locked`) that the in-workout screens address by `day_number`.

Unique: (`plan_id`, `day_number`). **Scheduled-date lock:** the backend refuses start / set / RPE / complete for a session (409, `_deny_unless_session_open` in `backend/app.py`) while `scheduled_date` is after today in `APP_TIMEZONE` (env, default `Asia/Kolkata`; see `app_today()`). **Missed days (strict):** a session with no `completed_at` whose `scheduled_date` is before today is *missed* (`is_session_missed`) — including one that was started with sets logged but never finished. Missed is derived, not stored (no column, no cron job): a missed session is refused the same way (409, `"missed": true`), shows as `missed` on the dashboard, and `next` moves past it. Once every session of a plan is completed or missed, the plan is closed via `mark_plan_completed` (which auto-progresses it) — either by `complete_session` when the last open session is finished, or lazily by `get_unfinished_plan` the next time anything loads the plan (dashboard, `/workout-plan`, progress-plan, admin), which then returns the new plan. `mark_plan_completed` only matches while `completed = false`, so racing closes progress a plan once. In progression, a missed session's exercises carry forward unchanged (same exercise, same reps) instead of taking the missing-RPE → hard path; reported joint pain still reduces them. Like a period session, a missed one is skipped when looking for the earlier week of the two-week hold, so the streak compares with the last completed week. Replaces the former `session_day_logs` table.

### Cardio days (`cardio_exercises` + cardio `sessions`)

Logic in `backend/cardio.py`. `create_plan` (and `create_progressed_plan`, which also adds them to a plan from before cardio existed) creates one `kind = 'cardio'` session on each of `CARDIO_DAYS[plan_type]` — days 2, 4, 6 for `3_day`, days 3 and 6 for `4_day` (day 7 stays a rest day). `DAY_TEMPLATES` itself is unchanged (the workout agent and the coach planner rely on its rest days); `_reconstruct_plan` / `_workout_entries` overlay those days as `split_name: "Cardio"`, `is_rest_day: false`, `kind: "cardio"`, with a `cardio` block (`rounds`, `work_seconds`, `rating`, rest timings, `estimated_seconds`, and the circuit's `exercises` with public `video_url` / `poster_url`). Everything else — date lock, missed rule, plan close, 25 points on completion — treats them like any session. Women get the same "are you on your period?" prompt on cardio days: a yes sets `is_period` as usual, and each exercise then runs 70% of its planned seconds, rounded, at least 15 s (`CARDIO_PERIOD_FACTOR`, `period_seconds`). That scaling is applied **when the session is read** (`_cardio_block`'s `work_seconds`, with the stored level as `planned_work_seconds`; `complete_session`; the analysis consumer) — `cardio_work_seconds` itself is never rewritten.

**The run:** the same warm-up video as strength days (skipped when resuming a session already started) → 10 s get-ready → each circuit exercise for `work_seconds` (its clip plays muted and looped under a seconds-left ring) → a rest a third as long as the exercise (`exercise_rest_seconds`: 30 s → 10 s, 60 s → 20 s; on a period day, a third of the shorter time) showing the next one → after a round's last exercise a 30 s round rest instead → … → `/day/:n/cardio/rate` (easy / about right / too difficult, "skip" = medium) → the same cool-down video → grow → summary. Not resumable mid-circuit: leaving restarts it. As each exercise and each rest ends, the PWA logs how it went (`PUT /api/sessions/<id>/cardio-log`, see `session_cardio_logs`); the client's View screen and the coach's Monitor clients show it (`CardioLog`), with a "Skipped N" chip on the coach's card.

**Progression (per week, `_cardio_next_level`):** everyone starts at 1 round × 30 s. The week's outcome is the most common `cardio_rating` among its completed cardio sessions, period sessions excluded (unrated counts as medium; ties go to the harder rating; nothing that votes → hold, so a week done entirely on her period keeps its level). Easy → +10 s up to 60, and at 60 s one more round back at 30 s. Hard → −10 s down to 15, and at 15 s one round fewer at 60 s (1 × 15 s is the floor). Medium holds once: it steps up only when the previous counted week (nearest ancestor plan with a completed non-period cardio session, up to `MAX_PROGRESSION_HOPS`) was also medium at the same level.

**`cardio_exercises`** — the circuit, in `position` order: `id` identity PK, `name`, `video_path` / `poster_path` (object paths in the **public** `cardio-videos` Storage bucket, 50 MB limit, mp4/jpeg), `position` int2 unique, `active` bool (inactive rows are left out), `created_at`. Seeded with 10 clips. The clips are re-encoded (720p, no audio) by `utilities/cardio_videos/prepare.sh` and uploaded by `utilities/cardio_videos/upload.py` (needs `SUPABASE_SERVICE_ROLE_KEY` in the environment). The backend caches the circuit for 5 minutes. The analysis consumer gets cardio sessions as `workout_type: "cardio"` with the circuit names, level, rating, a computed `compared_to_last_time`, and `what_happened` — `_summarize_cardio_log` over `session_cardio_logs`: exercises skipped (and how many seconds in), stopped early (< 80% of the time), never reached, long pauses (≥ 20 s), rests skipped; null when nothing was logged — which its clarifying questions use to ask why she skipped or stopped (one detailed question naming the exercises), plus the rating and the discomfort check.

### `session_analysis` — LLM-generated Tanglish summary per session

One row per session that's been analyzed. Written by the standalone `voice_processor` package (repo root, alongside `backend`/`frontend`; see "Voice processor" below) — a Kafka consumer, independent of the Flask app; this is its `summarizer` processor (`voice_processor/workout.py`). Those events are produced by `backend/kafka_producer` from the WhatsApp webhook (`backend/controllers/whatsapp_webhook_controller.py`) when the client shares a finished workout with the coach: the shared message carries a `Session ID: <sessions.id>` line (a rule, not a model, decides this), and the event is `{target: "summarizer", session_id, phone_number}` on `user-conversation`. On each event the consumer reads that session's `session_exercises` (with `session_exercise_set_logs` and `session_exercise_rpe` joined in), its plan, the user's `user_profiles.profile`, and their `user_joint_pain`. It transcribes the session's `feedback_audio_path` and every `session_exercises.feedback_audio_path` in parallel (`transcribe_many`; `KAFKA_MAX_POLL_INTERVAL_MS` defaults to 900000 to leave room), each recording with a Sarvam batch speech-to-text job (`stt/`, `saaras:v4`, `ta-IN`, `codemix`; `STT_JOB_TIMEOUT_SECONDS`, default 180) and passes the session transcript as `client_voice_feedback` and each exercise's as that exercise's `client_voice_note`. This is best-effort: a failed transcription is logged and the summary is written without it. It then prompts Claude (`claude-sonnet-5-5`, via the `anthropic` SDK with server-side refusal fallback; a refusal raises `SummaryRefusedError` rather than saving anything) to write (as structured output, `WorkoutSummary`: `summary` + `questions`) a **short check-in in Tanglish** (Tamil-majority, code-switching into English for gym/fitness terms — see `voice_processor/prompts.py`): an energetic greeting with no name (`user_profiles.gender`: female "Hi ma", male "Hi pa", else "Hi"); "I just checked your workout", saying everything looks great only when it does; at most **one** improvement, and only a real one — an exercise she moved up to (`progressed_from`: a `progression` edge in `exercise_relationships` from an exercise she did last time to this one) or one that felt too difficult last time and fine now (`felt_easier_than_last_time`), never just more reps; then **at most 3** clarifying questions (see "Voice-feedback agent"), exercise names said in English exactly as `exercises.name`. No question intro, no closing, no "reply with a voice note": the note ends on the last question. No audio tags. It upserts the result here. Each exercise in the context also carries its `loaded_joints` (from `exercise_loaded_joints`, load not `nil`), so earlier pain is only asked about when today's workout loaded that joint; cardio carries `previous_rating` for "felt easier". If the plan has a `parent_plan_id`, the consumer also fetches the parent plan's session for the **same `day_number`** (its exercises, set logs, RPE and start/completion times) and includes it as `previous_session` context, so the prompt can call out individual- and exercise-specific progress compared to the client's last time on that day of their split (see `AnalysisRepository._fetch_previous_session_context`). If that session was missed, it walks further up `parent_plan_id` (up to `MAX_PREVIOUS_PLAN_HOPS` plans) to the most recent completed one. The voice note is stored as `plan_<plan_id>/day_<day_number>.ogg`.

### Voice processor (`voice_processor/`)

One Kafka consumer (`python -m voice_processor.main`, run on the VM by systemd) on **one topic, `user-conversation`** (created on Aiven, 1 partition). Every event names the processor that handles it in `target`; `processors.py` holds the registry (`build_processors`, one `Processor` with `handle(payload)` per target) and `main.py` dispatches on it. Events are keyed by the client's phone (or `user_id`), so one client's events stay in order. Producer: `KafkaProducerClient.send_user_conversation_event(target, payload, key)` (returns whether it was delivered). Replaced the old `workout-complete-events`, `workout-feedback-replies` and `meal-log-events` topics on 2026-11-23.

| `target` | Produced by | Processor |
|---|---|---|
| `summarizer` | WhatsApp webhook: text with a `Session ID` line (`{session_id, phone_number}`) | `workout.handle_workout_complete` — summary, coach notes, clarifying questions (see `session_analysis` and below) |
| `router` | WhatsApp webhook: every voice note, and text without a `Session ID` (`{phone_number, whatsapp_message_id, type, text \| media_id}`) | `router.handle_inbound` — see "WhatsApp router" below |

Everything is synchronous: a router message (download, Sarvam, Haiku, then the reply flow or the diet pipeline and its WhatsApp reply) finishes before the next event starts, so a food check-in can wait behind a workout summary in progress.

### WhatsApp router (`inbound_messages`)

`voice_processor/router.py` (`handle_inbound`), Claude call in `router_agent.py`, prompt in `router_prompts.py`. Code-driven: Claude only returns a label, code acts on it.
1. The message gets an `inbound_messages` row (by `whatsapp_message_id`, so a redelivered one is skipped once `handled_at` is set).
2. The client is the one whose `user_profiles.whatsapp_number` is the sender (`get_profile_for_routing`); unknown numbers are `other`.
3. A voice note is downloaded from WhatsApp, stored as `inbound_<id>.<ext>` in `voice-feedback` and transcribed **once** with Sarvam (`diet.transcription.transcribe_audio_unrecorded`: synchronous endpoint ≤ 28 s, else a batch job); everything downstream uses that transcript and path (a redelivery reuses them).
4. Possible labels: `question_reply` only while the phone has an open, unexpired round (`find_open_clarification`); `diet_checkin` only while `user_profiles.diet_enabled`; `other` always. Only `other` possible → no Claude call.
5. `claude-haiku-5-5` (effort low, structured output via `client.beta.messages.parse`, label enum built per call; no server-side fallback on Haiku) gets the message, the open questions verbatim with minutes since asked, and the time in her zone (`user_profiles.timezone`), and returns `{label, day: today | yesterday, reason}`. A refusal or error → `other`. Recorded as `message_routing`.
6. `question_reply` → `workout.process_reply` with the transcript and path (see "Her replies"); `diet_checkin` → `log_meal`: a `meal_logs` row with `source = whatsapp`, `logged_for` today or yesterday in her zone (`day`, `diet/dates.py:today_in`), the router's audio path, run through `process_meal_log` with the transcript, then **meal feedback** (below) for a log of today, "Noted" for yesterday's food (or when the feedback fails), or a fixed Tamil "please send it again" when it ends `failed`; `other` → nothing.

**Meal feedback** (`voice_processor/meal_feedback.py`): a short Tanglish **text** (no voice note, no AI call, nothing stored but `feedback_sent_at`). Each meal the check-in mentions is judged **on its own** against its share of her daily targets (`MEAL_SHARES`: breakfast 25%, lunch 35%, snack 10%, dinner 30%), summing every `ready`/`confirmed` log of that meal today (a dish with no `meal` counts by time, `meal_reminders.meal_by_time`). The reply names her, then per meal a block of all five macros as eaten / target with ✅ within the tolerance band (`TOLERANCE`: kcal 10%, protein 10%, carbs 15%, fat 20%, fibre 20%), 🔻 short or 🔺 over (for a `gain` goal kcal is over only past 30%, `GAIN_KCAL_OVER`); an all-✅ reply adds a short encouragement; a last line lists the meals not logged yet today (`Innum log pannala: …`, skipped meals count as logged). A skipped meal gets a gentle nudge; a meal with a `needs_review` dish isn't judged. "Noted" for yesterday's food (or when the feedback fails), or a fixed Tamil "please send it again" when it ends `failed`. The older `meal_logs.feedback`, `feedback_flags` and `feedback_audio_url` columns are no longer written (old rows keep theirs).
7. The Sarvam cost is recorded once the route is known: `meal_stt` (diet), `reply_stt` (reply) or `inbound_stt` (other).

Try it without acting on anything: `.venv/bin/python -m voice_processor.router_dry_run --phone 91… --text "…"` (that client's real open questions and diet switch) or `--stored` (every stored WhatsApp reply and app food transcript, with the expected label; 17/17 on 2026-11-23).

**`inbound_messages`** — one row per routed WhatsApp message: `id`, `whatsapp_message_id` (unique), `phone_number`, `user_id` (nullable FK, cascade — null for unknown senders), `message_type` ∈ `text, audio`, `text`, `media_id`, `audio_path`, `transcript`, `route` ∈ `diet_checkin, question_reply, other` (null until routed), `route_reason` (Haiku's one-line reason), `route_model`, `clarification_id` (FK, set null), `meal_log_id` (FK, set null), `created_at`, `routed_at`, `handled_at`. Indexed on `user_id`, `clarification_id`, `meal_log_id`.

### WhatsApp reply window (`whatsapp_conversations`)

WhatsApp allows free-form (non-template) messages only for 24 hours after the client's last message; our messages don't extend it. The webhook records **every** inbound message, of any type and before any routing, via `WhatsAppRepository.record_inbound` (`backend/repository/whatsapp_repository.py`, best-effort — a failure is logged and the message is still handled), using Meta's `timestamp` on the message. It calls the SQL function `record_whatsapp_inbound(p_phone_number, p_at, p_message_id, p_type)`, which upserts the phone's row, keeps the **latest** time (Meta can deliver out of order or twice) and links `user_id` when the sender is a client's `user_profiles.whatsapp_number`.

**`whatsapp_conversations`** — one row per phone: `phone_number` PK, `user_id` (nullable FK, cascade), `last_inbound_at`, `last_inbound_message_id`, `last_inbound_type`, `first_seen_at`, `updated_at`. View **`whatsapp_reply_windows`** (`security_invoker`): `phone_number`, `user_id`, `last_inbound_at`, `window_expires_at` (+ 24 h), `window_open`; read with `WhatsAppRepository.reply_window(phone)`. Backfilled on 2026-11-23 from `clarification_replies` and `session_clarifications.asked_at` (a stand-in for the workout share just before it). Nothing reads it yet; it's there to check before sending anything outside a reply (reminders, late messages), which would need a template.

### Meal reminders (`meal_reminders`)

`voice_processor/meal_reminders.py`, run every 15 minutes by a systemd timer on the VM (`voice_processor/deploy/`: `meal-reminders.service` running `--due`, `meal-reminders.timer` with `OnCalendar=*:0/15`, `Persistent=false`; install steps in `deploy/README.md`). Reminders go out at **11:00, 15:00 and 20:00 in each client's own time zone** (`user_profiles.timezone`): a slot is due while her local time is between its time and 45 minutes after (`SLOT_TIMES`, `DUE_WINDOW_MINUTES`, `due_slot`), so she's reminded within 15 minutes of it, and a pass missed for longer is skipped rather than sent late. `--slot breakfast|lunch|dinner` runs one slot for everyone now (manual runs); `--dry-run` prints decisions and sends nothing; `--user-id` for one client. For each client with `diet_enabled` and `diet_setup` done and a slot due:
1. A `meal_reminders` row for (her, her local date, slot) already exists → nothing.
2. Missing = the meals due by the slot (`SLOT_MEALS`: breakfast; breakfast + lunch; breakfast + lunch + snack + dinner) minus the meals of the `ready`/`confirmed` logs with `logged_for` = her local date, including meals she said she skipped (a dish with no `meal` counts by the log's time in her zone: < 11 breakfast, < 16 lunch, < 19 snack, else dinner). A meal she has logged is never asked about again. Nothing missing → `skipped_logged`.
3. No `whatsapp_number`, or `whatsapp_reply_windows` for it closed or absent → `skipped_window_closed` (no templates are sent).
4. Otherwise the row is inserted as `pending` first (so a crash can't cause a second send), a fixed Tanglish text of at most 10 words naming her (`user_profiles.name`) and only the missing meals (`reminder_text`, e.g. "Priya, lunch innum log pannala 🙂") is sent as plain text to her `whatsapp_number` (no voice note, no Sarvam cost; `audio_url` is no longer written) → `sent`, or `failed` with `error`; the pass moves on to the next client.

Her answer comes back through the router, which for 3 hours after a `sent` reminder (`REMINDER_HINT_HOURS`, `AnalysisRepository.recent_meal_reminder`) adds `meal_reminder: {asked_about, minutes_ago}` to Haiku's input — food mentioned then is a diet check-in.

**`meal_reminders`** — `id`, `user_id` (FK, cascade), `reminder_date` (her local date), `slot` ∈ `breakfast, lunch, dinner`, `missing_meals` text[], `status` ∈ `pending, sent, skipped_logged, skipped_window_closed, failed`, `audio_url`, `error`, `created_at`, `sent_at`. Unique (`user_id`, `reminder_date`, `slot`); indexed on (`user_id`, `sent_at`).

### Voice-feedback agent (`workout_comments`, `session_clarifications`, `clarification_replies`)

Lives in `voice_processor` (`feedback_agent.py`, `feedback_prompts.py`, wired in `workout.py`). Claude (`claude-sonnet-5-5`, structured outputs via `client.beta.messages.parse`, server-side refusal fallback) only *proposes* notes; `validate_note` drops any note whose `quote` isn't really in what the client said (case/punctuation/space-insensitive), unlinks exercises not in the session and joints not in `joints`.

**After a workout share** (`_process_message`): the transcripts go to `extract_feedback`, whose notes replace the session's voice-note rows in `workout_comments` (so a redelivered event doesn't duplicate) and update `user_joint_pain` — **overwrite**: within one batch the worst level per joint wins, `pain_resolved` deletes the row, and a later batch simply overwrites (`joint_pain_changes`, `AnalysisRepository.apply_joint_pain`). Notes flagged `urgent` (chest pain, dizziness, …) are logged as warnings. The notes are passed to the summary as `client_feedback_notes`, along with `previous_questions_and_answers` — the questions (both rounds) and answer summaries from her last 8 sessions that had any (`AnalysisRepository.fetch_question_history`, `MAX_QUESTION_HISTORY_SESSIONS`, newest first, current session excluded), which the prompt uses to follow up on unsettled pain or repeated difficulty and to avoid re-asking what she already answered; **the summary's input is plain text, not JSON** (`voice_processor/summary_input.py`, `render_context`): one field per line, one line per exercise led by its `session_exercise_id`, set logs as `set_logs 10, 9, 9`, unset values left out (a `-` for `effort_flag` was misread as a rating), and the history grouped into topic threads (`history_threads`: per exercise / joint / general question per workout type — the latest English intent, times asked, latest real answer or "never answered", every earlier answer for a joint thread, one otherwise; the Tamil wording is dropped). The model still picks every question. Tested on 20 real sessions on 2026-11-25: input −33%, cost −14%, question quality unchanged; the summary's questions (priority: earlier pain, only if one of today's exercises loads that joint → why too hard → what stopped unfinished sets → a problem from her voice notes → too easy, how many more reps → whether a new exercise was clear; no general "any other discomfort" on strength days, cardio days always end with one) are validated (`validate_questions`, ids `q1…`, max 3 — `MAX_QUESTIONS` — and only the first question per `session_exercise_id` kept) and spoken in the same voice note (`spoken_text`: the check-in, then the questions — the whole text is what `session_analysis.analysis` stores). **Voice:** the summary and the follow-up notes are spoken by **ElevenLabs** (`tts.ElevenLabsTTSClient`, `eleven_v4_turbo`, the coach's cloned voice `ELEVENLABS_VOICE_ID`, `language_code` `ta`, plain text, mp3 → the usual WhatsApp OGG) via `voice.generate_voice_note`; any ElevenLabs failure (missing `ELEVENLABS_*`, out of credits) falls back to Sarvam, and the cost row records whichever spoke it. Meal feedback and meal reminders are plain WhatsApp texts, with no voice note. The round-1 `session_clarifications` row is saved **before** the audio is sent (and the phone's older open rounds are superseded); if there's no audio, the questions go as a text message.

**Her replies:** every WhatsApp voice note or text without a `Session ID` line goes to the router (above); one it labels `question_reply` is handed to `workout.process_reply` with her open round, the transcript and the stored audio (`inbound_<id>.<ext>`, nothing downloaded again). It records the message in `clarification_replies` (deduped by `whatsapp_message_id`; `audio_path` / `transcript` copied from the router) and runs `map_reply` (input sent as plain text like the summary's — `render_reply_input`: one line per question with its intent, the exercises, the history as topic threads, and her reply last, verbatim, since note quotes are checked against it), which maps the answer onto question ids, extracts notes (stored with `source = clarification_reply`, `question_id`, `clarification_reply_id`; same pain rules) and, in round 1 only, may ask at most 2 follow-ups (it gets the same 8-session question history, to ask how an earlier problem compares instead of re-asking it). Follow-ups → round 1 closes (`answered`/`superseded`), a round-2 row opens and they're sent as a voice note (`plan_<plan_id>/day_<n>_followup.ogg`); everything answered → `answered` plus a fixed Tanglish thank-you text; otherwise it just records the answers and waits.

**`workout_comments`** — one row per observation. `id`; `user_id` (FK, cascade); `session_id` (FK, cascade); `session_exercise_id` (nullable FK, cascade — null = about the whole session); `exercise_id` (nullable FK → `exercises`, `ON DELETE SET NULL`, denormalized for per-exercise history); `category` ∈ `difficulty, joint_pain, pain_resolved, discomfort, fatigue, technique, enjoyment, other`; `difficulty` ∈ `too_easy, about_right, too_hard`; `joint_id` (FK → `joints`) / `pain_level` ∈ `mild, moderate, severe`; `urgent` bool; `comment` (English coach note); `quote` (her exact words); `source` ∈ `session_voice_note, exercise_voice_note, clarification_reply`; `clarification_reply_id` (nullable FK, cascade); `question_id`; `created_at`.

**`session_clarifications`** — one row per round of questions. `session_id`, `user_id` (FKs, cascade), `phone_number` (from the share event), `round` (1, or 2 for follow-ups), `questions` jsonb `[{id, text, intent, topic, session_exercise_id, joint}]`, `answers` jsonb `{question_id: {summary, reply_id}}`, `status` ∈ `open, answered, superseded, expired` (expired lazily after `expires_at` = asked + 24 h, WhatsApp's free-form reply window), `asked_at`, `closed_at`. Unique (`session_id`, `round`); a redelivered event re-opens a round only if it has no replies yet.

### AI Coach agent (`coach_suggestion_runs`, `exercise_suggestions`)

Admin-only. In Monitor clients, each **scheduled strength** workout card has an AI coach panel (`frontend/src/screens/admin/CoachSuggestions.tsx`): "Get AI suggestions" calls `POST /api/admin/sessions/<id>/suggestions` (`backend/controllers/admin_coach_agent_controller.py`, `X-Admin-Key`; 409 unless scheduled and strength), which runs the agent **inside the request** (~20–30 s; `claude-opus-5-5`, effort medium, structured output via `client.beta.messages.parse`, server-side refusal fallback, `COACH_AGENT_TIMEOUT_SECONDS` default 55, no retries — 502 on failure). Code in `backend/coach_agent/`:
- `context.py` (`build_context`, reads via `repository.py`'s `CoachAgentRepository` on the plan repo's Supabase client): the client (full profile, joint pain, recent period days, week's coach notes, safety summary); every exercise with min–max, prescribed sets and per-set reps, loaded joints with load, `avoid_if`, and its progression/regression options from `exercise_relationships` (the only allowed swap targets); the same `day_number` in the previous two plans (walking `parent_plan_id`) with prescribed vs logged reps and RPE; the questions/answers of her last 8 sessions (a backend copy of the consumer's shaping); her 40 latest `workout_comments`. It also returns the `facts` validation checks against.
- `prompts.py`: one suggestion per open exercise — `keep` (the default), `adjust` (1–6 sets, targets within min–max), `progress`/`regress` (to a listed option; default targets its min / max), `skip` (this workout only) — each with a reason and evidence (`client_answer`/`client_comment` quotes must be her exact words; `set_logs`, `rpe`, `joint_pain`, `profile`, `coach_note`, `progression_rule` state facts), plus an `overview` for the coach. Explains the progression engine so it only adds what the algorithm can't see.
- `validate.py` (pure): anything invalid (out-of-range targets, a non-edge swap, a foreign exercise, no reason, no surviving evidence — client quotes not found in her answers/comments are dropped) falls back to `keep` with the reason saying why; a no-op adjust becomes keep; locked (sets logged) and skipped exercises get no row; every open exercise gets exactly one.
- `dry_run.py`: `.venv/bin/python -m backend.coach_agent.dry_run --user-id <id>` (her next scheduled strength workout) or `--session-id N` prints the full prompt, raw response and validated suggestions without storing anything.

**`coach_suggestion_runs`** — one row per click: `id`, `session_id`, `user_id` (FKs, cascade), `overview`, `model`, `created_at`. **`exercise_suggestions`** — one row per exercise per run: `run_id` (FK, cascade), `session_exercise_id` (FK, cascade), `action` ∈ `keep, adjust, progress, regress, skip`, `proposed_sets`, `proposed_reps` (stored like `session_exercises.reps`), `proposed_exercise_id` (FK → `exercises`, set null), `before` jsonb (`{exercise_id, name, sets, reps}` when suggested), `reason`, `evidence` jsonb (`[{source, quote, session_id, verified}]`), `status` ∈ `pending, accepted, rejected, no_change, superseded` (a new run supersedes the session's pending ones), `decided_at`, `created_at`. `GET /api/admin/sessions/<id>/suggestions` returns the latest run. `POST /api/admin/exercise-suggestions/<id>/accept` re-checks (still pending, workout still scheduled, no sets logged, exercise unchanged since `before` — else 409) and applies it like the coach's own edit (`update_session_exercise_prescription`, with the swap for progress/regress, or `set_session_exercise_skipped`), so it becomes next week's baseline and restarts the two-week hold; `.../reject` marks it rejected.

### Voice diet tracking (`meal_logs`, `meal_log_items`, `meal_log_item_ingredients`, `ingredient_nutrition_reference`)

Code in the root package `diet/` (shared by the backend and its own consumer, like `stt/`). Rewritten on 2026-11-20: there is no dish library any more (the old `foods`, `ingredients`, `food_ingredients`, `food_portions`, `user_food_ingredients` tables, the coach's Foods tab and "her own version" of a dish are gone) — every recording is worked out from scratch by Sonnet. **Off by default, switched on per client by the coach:** `user_profiles.diet_enabled` (bool, default `false`) is set from the Food card in Monitor clients (`PATCH /api/admin/users/<user_id>/diet-tracking` `{"enabled": bool}`). While it is off, every client diet endpoint answers 403 (`"diet_disabled": true`, the `require_diet` guard in `diet_controller.py`), `/api/auth/me` and sign-in return `diet_enabled: false`, and the PWA shows no Diet tab and redirects `/food…` to the dashboard (`RequireDiet` in `App.tsx`). The app reads the flag when it loads, so a change shows the next time she opens it. **One-time setup:** the first time she opens Diet (`user_profiles.diet_setup` still null; `/api/auth/me` and sign-in return `diet_setup_done`), every `/food…` route sends her to `/food/setup` (`DietSetupScreen`, all copy in Tamil script): height (cm, 120–220), weight (kg, 30–200) and age (15–90) on scroll wheels (`components/WheelPicker.tsx`) → `POST /api/users/<user_id>/diet/setup/assess` (stores nothing) returns her BMI, its category (WHO: < 18.5 underweight, ≥ 25 overweight) and the recommended goal (gain / maintain / lose), which she confirms ("we think you may need to…, is that right?") or, on "no", replaces with her own pick. A goal is only offered (and accepted) when it has a target weight within a healthy BMI: lose needs room above the BMI 18.5 weight, gain room below the BMI 24.9 weight — so no losing when underweight, no gaining when overweight. For lose / gain she then picks a **target weight** on a wheel (`target_weights` from `/assess`: the range plus our suggestion, a first step — 10% down but not below the BMI 24.9 weight when overweight; up to the BMI 18.5 weight, at most +5 kg, when underweight; +3 kg when healthy) → `POST /api/users/<user_id>/diet/setup` `{height_cm, weight_kg, age, goal}` works out her targets (`diet/setup.py`: Mifflin-St Jeor BMR with sex from `user_profiles.gender` (midpoint −78 for other/unset) × 1.375 lightly active; gain +300 kcal; lose − min(500, 20%) when overweight, − min(250, 10%) (gentler) when her BMI is already healthy, never below BMR or 1200 (1500 for men); rounded to 10; protein 1.2 g/kg of her weight capped at BMI 24.9's weight; fat 25% of calories; fibre 14 g/1000 kcal, at least 25; carbs the rest) and stores them as `nutrition_targets` together with `diet_setup` in one conditional update (only while it's null, so it happens once; 409 afterwards) and the **timeline** to her target (weekly kg = daily kcal change × 7 / 7700, `weeks`, `target_date`; none when the floors leave under 100 kcal of change) → a result card (with the target and timeline) → the tracking screen. The coach sees the setup line on the Food card and can still override the targets. Turning it off keeps what she logged; the coach can still see it by turning it back on. A client records what she ate on the PWA's Food screen (`/food`, reached from the Diet tab of the bottom bar). Amounts are estimates.

**Flow:** `POST /api/meal-logs` (multipart `audio`, `day`: `today` | `yesterday`; same audio types and 4 MB limit as voice feedback — `read_audio_upload` in `backend/feedback_storage.py`) stores `meal_<id>.<ext>` in the private `voice-feedback` bucket, inserts a `meal_logs` row (`processing`, `source = app`) and publishes `{target: "diet", meal_log_id}` to `user-conversation` (`KafkaProducerClient.send_user_conversation_event`; undelivered → the log is marked failed and the request answers 502). The voice processor (`python -m voice_processor.main`; see "Voice processor" above) hands each event to `diet/pipeline.py:process_meal_log`. **WhatsApp check-ins** go through the same pipeline: the router (see "WhatsApp router") creates the log itself (`source = whatsapp`, today or yesterday as she said, never reviewed so it stays `ready`), passes its transcript in instead of transcribing again, and answers on WhatsApp ("Noted", or a Tamil retry message). The coach's Food card shows a WhatsApp chip on those logs (`source` on each log). Events are handled one at a time, so a food log can wait behind a workout analysis that is in progress:
1. **Transcribe** (`diet/transcription.py`): recordings ≤ 28 s go to Sarvam's synchronous endpoint (`SarvamRestSTTClient`, about a second); longer ones, or a failure, to a batch job. Same `saaras:v4` / `ta-IN` / `codemix`.
2. **Estimate** (`agent.estimate_meal`, `claude-sonnet-5-5`, structured output via `client.beta.messages.parse`, server-side refusal fallback, prompt in `diet/prompts.py`): Claude gets **only** the transcript and the ingredient **names** of `ingredient_nutrition_reference` (one per name, `no data` rows left out; `DietRepository.reference_ingredients`, cached 5 min; the prompt is not cached — recordings are usually further apart than the cache lasts) — no nutrients, no dish catalogue. It returns every dish she ate: `quote`, `dish_name`, `dish_name_ta` (Tamil script), `quantity` + `unit` (piece, karandi, cup, tumbler, tablespoon, teaspoon, plate, bowl, handful, slice, grams, ml), `quantity_stated`, `meal`, `portion_grams` (cooked weight of her portion) and `ingredients` — the **raw grams of each ingredient in her portion**, typical Tamil Nadu home recipe, oil/ghee/sugar/coconut/salt included, water and pinch spices left out. The ingredient `name` is an enum of the reference names (`agent.meal_schema`, built per name list), so Claude can only pick from the table (the closest one when the exact ingredient isn't there).
3. **Validate** (`validate.validate_meal`): drops a dish whose quote isn't in the transcript or that has no name; clamps quantities (0.25–20; 1–2000 for grams/ml); merges duplicate ingredients; a dish whose portion weight (1–2000 g), ingredient lines (each 0–1500 g, 1–25 of them) or raw total (over 2.5× the portion weight; no lower bound, since water is left out and watery dishes like koozh or a shake are rightly light) can't be right is kept with `needs_review` and no ingredients. No amount said → `assumed`.
4. **Save** (`build_item_rows`, `repo.replace_items`): each dish becomes a `meal_log_items` row with its ingredient rows (`grams` = `default_grams` = Claude's amount, linked to the reference row) and its **nutrient totals** (`nutrients` jsonb: every nutrient column of the reference table, summed from grams × per-100 g values, null counted as 0 — `diet/nutrition.py`). Meals she says she **skipped** ("breakfast skip pannitten", "lunch saapdala") come back as `skipped_meals` (validated by `validate.validate_skipped`) and are stored on the log. The log becomes `ready` (with `model`) when it has dishes **or** skipped meals — a skipped-only log is ready with no items, so WhatsApp answers "Noted" — or `failed` with `error` ∈ `no_speech`, `no_food` (neither), `failed`. A log still `processing` after 5 minutes reads as `failed` / `timeout` (`service.log_status`; derived, not stored).

Totals are **stored**, not computed at read time: correcting the reference table doesn't change past days. Every edit recomputes the item's `nutrients` from its ingredient rows (`service._save`). Day totals sum the stored `nutrients` of `ready` and `confirmed` logs.

**Her screens are in Tamil script** (strings in `frontend/src/foodText.ts`, units and meal names in `food.ts`, the setup's own in `DietSetupScreen`; dates via `Intl` `ta-IN`; API error text is replaced by a Tamil fallback; numbers, g/kcal and ingredient names stay as they are; the Diet tab too, the rest of the app stays English). Dishes show `name_ta` (`meal_log_items.dish_name_ta`: Claude's Tamil-script name for the dish, kept only if it contains Tamil letters and is ≤ 80 characters, else null → the English `dish_name`). **Her screens:** `/food` (`FoodScreen`, "Your Food": a **Today** / **Past 10 Day Logs** switch. Today shows the Daily Goal card — a calorie ring plus protein, fibre, carbs and fat bars with % of her targets — the day's dishes by meal, and a floating mic ("Tap to record"; the recording is sent as soon as she stops and is always for today). Past 10 Day Logs is a "Nutrition Overview": a bar chart each for calories, protein, carbs, fibre and fat over the last 10 days (today on the right, darker), a dashed line at her target, and the average over the days she logged anything (`GET /api/users/<user_id>/diet/days?days=10`, 1–61: each day's goal totals and dish count, empty days included); tapping a bar opens that day's goal card and dishes. The mic shows on both tabs and always records for today). Clients with diet tracking on also get a fixed bottom bar on `/` and `/food` with two tabs, **Workouts** (the dashboard, where the app opens) and **Diet** (`components/BottomNav.tsx`; while shown it adds `with-bottom-nav` to `body` so those screens leave room), `/food/log/:id` (`MealReviewScreen`: polls `GET /api/meal-logs/<id>` every 2 s, then a card per dish with − / + and remove; Done = `POST …/confirm`, Record again = `DELETE`), `/food/item/:id` (`MealItemScreen`: the dish's ingredients with the amounts assumed for her portion). Endpoints in `backend/controllers/diet_controller.py`, own logs only (404 otherwise): `PATCH /api/meal-log-items/<id>` `{quantity}` scales the portion weight and all its ingredient rows (and their `default_grams`); `DELETE /api/meal-log-items/<id>`; `PATCH /api/meal-log-items/<id>/ingredients/<reference_id>` `{grams}` (0–2000, 0 = removed) changes that row on this entry only; `POST /api/meal-log-items/<id>/reset` puts every ingredient back to its `default_grams`; `GET /api/users/<user_id>/diet?date=` is her day (calorie, protein, fibre, carb and fat totals, targets, logs). Per dish she sees protein; oil/ghee, sugar and salt are shown in teaspoons (`nutrition.display_unit`, by reference category).

**Coach:** Monitor clients has a Food card (`frontend/src/screens/admin/ClientFood.tsx`, `GET /api/admin/users/<user_id>/diet?days=7`, 1–60): every nutrient per day (labels in `screens/admin/foodLabels.ts`), and per log the transcript, recording (`GET /api/admin/meal-logs/<id>/audio`, signed URL), items with ingredients and what was assumed / edited / not worked out; plus her targets (`PATCH /api/admin/users/<user_id>/nutrition-targets`, any of `energy_kcal` (500–5000), `protein_g`, `fibre_g`, `fat_g` (1–500), `carbs_g` (1–1000); null = default; `TARGET_RANGES`).

`ai_usage` features: `meal_stt` (app recordings and WhatsApp check-ins), `meal_estimation` (older rows may show `meal_parsing`, `recipe_estimation`, `ingredient_nutrients`). The Costs tab has a Food tracking section (`summarize_food` in `admin_cost_controller.py`): cost by model, and per client recordings processed / failed (only `meal_stt` / `meal_estimation` spend from the period's first recording on — older rows belong to recordings that no longer exist, such as the logs dropped in the rewrite; the old features still show in the per-feature totals). View **`ai_usage_monthly`** (`security_invoker`): per user × month (in `Asia/Kolkata`) × provider × feature — records, calls, tokens, audio seconds, characters, `cost_usd`, `cost_inr`, `cost_inr_total`.

**Costs dashboard:** the `/admin` **Costs** tab (`frontend/src/screens/admin/CostsTab.tsx`) reads `GET /api/admin/costs?days=30` (`backend/controllers/admin_cost_controller.py`, `X-Admin-Key`; `days` 1–365, default 30; `include_dry_runs=1` to count `dry_run_` rows, left out by default). It pages through `ai_usage` (1,000 rows per request) and `summarize_costs` returns the period's total (Claude / Sarvam / ElevenLabs split, calls, clients with spend, average per client), per-feature totals, and one entry per client, highest spend first: total, Claude, Sarvam, ElevenLabs, workouts with spend and average cost per workout, last activity, and a per-feature breakdown (shown when the row is expanded). Rows with no `user_id` are grouped as `(unattributed)`. Period choices in the UI: 7 / 30 / 90 days.

### Admin client monitor

The PWA's `/admin` page has two tabs: **Onboard client** (profile → plan → review) and **Monitor clients**. The monitor reads through `backend/controllers/admin_monitor_controller.py` (both `X-Admin-Key`): `GET /api/admin/users` (every `user_profiles` row with `has_passkey`) and `GET /api/admin/users/<user_id>/monitor` (profile basics from `profile`, `user_joint_pain`, `user_period_logs` days, passkey count / last sign-in from `user_passkeys`, and `WorkoutPlanRepository.get_user_workout_history`: every session of every plan split into scheduled vs past, each with status/date (`workout_status`, shared with the dashboard), `is_period`, `has_feedback`, its `session_analysis` text + `audio_url`, duration, and exercises whose `rpe_logged` says whether effort was actually rated). Loading it never writes — unlike `get_unfinished_plan`, it doesn't close or progress plans. The one write is `PATCH /api/admin/session-exercises/<id>` (`{"sets": n, "reps": [one target per set], "note": "..."}`, reps or seconds, 1–10 sets, targets 1–600; `note` optional — the exercise's coach note, ≤ 500 chars, blank clears, left out keeps it; `exercise_id` optional — swaps the slot to another library exercise, also setting `rep_range` from its min/max, with the targets sent meant for the new exercise; the response then carries the new exercise's display fields as `exercise`. The PWA's editor picks it from the plan-builder library (`GET /api/admin/plan-builder`), same movement type listed first): the coach editing an exercise of a workout that is still **scheduled** and has none of that exercise's sets logged (else 409). It's stored the way progression writes `reps` (one number if all sets match, else a per-set list) and becomes the baseline next week's progression starts from — so an edit also restarts that exercise's two-week hold. The client's voice feedback is played through `GET /api/admin/sessions/<id>/feedback-audio` (signed URL, fetched when the coach presses play). Coach notes on the current week (`plans.coach_notes`, shown at the bottom of the client's dashboard) are edited with `PATCH /api/admin/users/<user_id>/coach-notes` (`{"coach_notes": "..."}`, blank clears, ≤ 2000 chars; 409 with no unfinished plan) and returned on the monitor as `current_plan`. Progression copies them into each next plan, so an edit carries forward. **Create progression** (`POST /api/admin/users/<user_id>/regenerate-plan`, `WorkoutPlanRepository.regenerate_current_plan`) deletes the client's current unfinished plan and re-runs `create_progressed_plan` from its `parent_plan_id`, keeping the same `scheduled_date`s — for after progression rules or inputs (e.g. RPE) changed. Refused (409, `PlanRegenerationError`) when there's no current plan, it has no parent (a first plan), or any of its sessions has `started_at`. The delete comes first (only one unfinished plan allowed), so a failure after it leaves no current plan until it's retried.

### Passkey authentication tables

Written by `AuthRepository` (`backend/repository/auth_repository.py`) via the passkey endpoints in `backend/controllers/auth_controller.py`; session cookies and route guards live in `backend/auth.py`. Enrollment is coach-issued: `POST /api/admin/users/<user_id>/enrollment-link` (requires `X-Admin-Key`) mints a one-time link; the user opens it in the PWA and creates a passkey. Session and enrollment tokens are stored only as SHA-256 hashes. All `user_id` FKs → `user_profiles.user_id` `ON DELETE CASCADE`, indexed.

**`user_passkeys`** — one row per registered passkey.

| Column | Type | Notes |
|---|---|---|
| `id` | int4 PK | `GENERATED BY DEFAULT AS IDENTITY` |
| `user_id` | text, FK | |
| `credential_id` | text, unique | base64url credential id — looked up on every sign-in |
| `public_key` | text | base64url COSE public key |
| `sign_count` | int8, default 0 | synced iCloud/Google passkeys always report 0 |
| `transports` | text[], nullable | as reported by the browser (e.g. `internal`, `hybrid`) |
| `aaguid` | text, nullable | authenticator model id |
| `backed_up` | bool, default `false` | whether the passkey is synced (backup state) |
| `created_at` / `last_used_at` | timestamptz | |

**`auth_challenges`** — pending WebAuthn challenges (5-minute expiry). Each `/verify` call reads the challenge back out of the credential's `clientDataJSON` and deletes the matching row in a single `DELETE`, so a challenge works at most once. Columns: `id`, `challenge` (text, unique, base64url), `purpose` (check ∈ `registration, authentication`), `user_id` (nullable — null for sign-in, since sign-in is username-less), `expires_at`, `created_at`. Expired rows are deleted opportunistically on each `POST /api/auth/login/options`.

**`auth_sessions`** — signed-in sessions behind the `fc_session` HttpOnly cookie (30-day expiry). Columns: `id`, `user_id`, `token_hash` (text, unique), `created_at`, `expires_at`, `last_seen_at` (bumped by `GET /api/auth/me`). Deleted on logout.

**`passkey_enrollment_tokens`** — coach-issued one-time sign-up links (48-hour expiry). Columns: `id`, `user_id`, `token_hash` (text, unique), `expires_at`, `used_at` (nullable — set once by a conditional `UPDATE` when enrollment succeeds), `created_at`. Minting a new link deletes that user's older unused ones.

### Notes on FK delete behavior

`movement_type_id` and `equipment_id` on `exercises`, `exercise_id` on `session_exercises`, and `joint_id` on `user_joint_pain`, have no cascade, so deleting a referenced row is blocked while referenced. `user_id` on `plans`, `user_joint_pain`, and the four passkey-auth tables is `ON DELETE CASCADE` — deleting a `user_profiles` row cascades to that user's `plans`, `user_joint_pain`, passkeys, auth sessions, enrollment tokens and pending challenges; `plans` in turn cascades to `sessions` via `plan_id`, `sessions` to `session_exercises` and `session_analysis` via `session_id`, and `session_exercises` cascades further to `session_exercise_set_logs` and `session_exercise_rpe` via `session_exercise_id`. `sessions` also cascades to `session_cardio_logs`; deleting a `cardio_exercises` row only nulls `session_cardio_logs.cardio_exercise_id` (the copied name stays). So deleting a `user_profiles` row transitively deletes all of that user's data across every child table. The join/edge tables (`exercise_loaded_joints`, `exercise_relationships`) cascade on delete from `exercises`. `plans.parent_plan_id` (self-referential) is the one exception to the "no cascade blocks delete" rule: it's `ON DELETE SET NULL`, so deleting a parent plan merely nulls out its children's `parent_plan_id` rather than being blocked or cascading further. Indexes exist on all FK columns.
